# Seatline performance implementation tracker

## Goal and scope

Reduce first-visible-text latency and recurring local overhead while keeping one shared companion safe for Tabbeam, Conclave, and Lineleaf. A warm broker, a resumed conversation, and a reused provider process are different states; report them separately.

Seatline owns provider execution, transport, readiness, scheduling, and cleanup mechanics. Applications retain prompts, conversation policy, orchestration, editor behavior, and product-specific preparation triggers. Keep the runtime Rust-based; do not add a JavaScript runtime or move Conclave features into Seatline.

Source review baseline: [`dc1086582c8b98498aa48dae91c8d174bc3cfc3c`](https://github.com/davletovb/seatline/tree/dc1086582c8b98498aa48dae91c8d174bc3cfc3c), rechecked against main on 2026-10-03. These are source-backed findings, not measured live-provider speedups.

## Workflow

- **READY**: dependencies satisfied; implementation may start.
- **IN PROGRESS**: actively being implemented.
- **BLOCKED**: finish the listed dependencies or protocol investigation first.
- **DEFERRED**: intentionally skipped pending an explicit project decision.
- **IMPLEMENTED — VERIFY**: code and local checks complete; PR/platform/integration validation remains.
- **DONE**: merged and the stated acceptance evidence is recorded.
- **EXTERNAL**: tracked here, but implementation belongs in an application repository.

Update this file in every implementation PR. Record commit/PR, relevant checks, measured evidence, and limitations. Verify each finding against the current code before changing it. Complete coherent slices; do not mark plans, prototypes, skipped live tests, or app work as finished library behavior.

## Implementation order

1. A: fix lifecycle bounds and remove the fixed startup delay.
2. B: establish reproducible phase measurements before claiming speedups.
3. C and D: define readiness freshness and reuse transport safely.
4. E: **deferred by user decision on 2026-10-04** pending the decision about Codex app-server; do not start the persistent-provider slice yet.
5. F: move blocking work off the hub, improve fairness, and reduce idle overhead.
6. G: validate and adopt the changes in all three applications.

D-01 and parts of B can proceed independently of C. Persistent-provider production rollout depends on B, C, and isolation/recovery evidence, rather than prototype existence alone.

## Verification and release gates

- Required for each Rust slice: formatting, workspace Clippy, workspace tests with the lockfile, affected regression tests, and the client-only companion build.
- Existing CI remains responsible for OS matrix, minimum Rust 1.85, release tests, runtime independence, and fuzz smoke. Real-provider tests remain opt-in.
- Lifecycle gates: one terminal event per accepted request, bounded cancellation/finish, eventual child reaping, no leaked occupied slots, no cross-app context or grant leakage.
- Performance gates: publish reproducible before/after evidence; preparation time and total cold work remain visible. A genuinely cold machine still has startup work, and network/model latency is outside Seatline's direct control.
- No automatic application pin updates or default persistent-mode rollout until the corresponding integration evidence exists.

## I — Answer latency: relay delivery, Claude effort, and where the time goes — 2026-10-09

Owner: Seatline/application maintainers. Status: **I-01 to I-06 IMPLEMENTED — VERIFY**, I-04 and I-05 for Claude only (the Codex, Gemini and Grok baselines are the owner's to run, and Antigravity's and Grok's wait after the answer is unmeasured); I-07 to I-11 are planned, each with the gate it waits on. Slice E stays **DEFERRED** pending the Codex app-server decision.

The question was what is left to speed up between a request and the model's answer. Seatline's own share is small and mostly spent: a warm request reaches first text in about 1.5 ms with a fake provider ([F](performance-baselines/2026-10-04-f-hub-summary.md)), and the owner's manual timing recorded in H-03 put 19,009 ms of a 19,147 ms Lineleaf check in the answer phase, 138 ms (0.7 %) anywhere else. What remains is in how each provider CLI is launched and ended, in waits around the answer, in what the model is asked to do, and in not knowing where the answer time goes. These findings were source-backed when the slice began, and I-04 has since measured the Claude ones live. **No item here has yet been shown to speed up a real answer**: I-04 priced what an answer costs, not what a change saves.

What the review found:

- **Claude loads the user's whole setup on every turn.** `claude -p` runs the user's hooks, plugins, skills and `CLAUDE.md` unless told not to. In a scratch home holding two synthetic 1-second hooks, Seatline's exact arguments took 5.7 s and the same arguments with `--safe-mode` 2.8 s (one run each, Claude CLI 2.1.295; that CLI had credentials of its own, so both runs sent a one-word prompt to a model). It is an observation, not a baseline: the cost on a real machine depends on its hooks. I-04 then measured this sandbox's own home, which loads almost nothing of its own (safe mode dropped one skill, one agent and one command), and found no measurable difference there.
- **Three adapters wait up to 5 s for the process after the answer.** Claude, Antigravity and Grok hold `Completed` until the CLI exits (`turn_ended` in the Claude adapter, and the `FINISH_GRACE` of the other two); only a successful ephemeral Codex turn was changed (H-02). How long the wait is in practice was unmeasured, because telemetry marked the terminal update only after the process was gone, so the wait sat inside `completion`. I-04 measured it for Claude: about 0.5 s (p50 0.50 s over 150 prompts, 0.38 to 0.80 s in 149 of them), a fifth of a one-word answer and the CLI's own exit time. Antigravity's and Grok's are still unmeasured. I-05 ended the wait for Claude (below): a signal turned out not to shorten it and a kill leaves the CLI's session files behind, so a turn that keeps no session now completes at the result, and the process is left to exit on its own.
- **Readiness evidence lapses after 30 s** (`seatline_core::readiness::MAX_AGE`), so the first check after a quiet half minute runs a sign-in probe before generating. `claude auth status` took 280 to 570 ms here, and 0.21 to 0.24 s in the live baseline; `codex login status` was not timed. Claude's evidence survived the turns between one `prepare` and the next, six of six, in the live baseline.
- **At most two generations run per app and per provider**, a ceiling `scheduling.json` cannot raise (`Policy::validate`), so an application that splits one long job into parallel requests queues the third.
- **Codex reports each message whole**, so the first text of a one-message answer arrives with its end. Incremental text needs the app-server protocol (E-01).
- **The relay WebSocket left Nagle's algorithm on**: `connect_async` does not set `TCP_NODELAY`, and every event is its own small frame.
- **Claude's CLI has `--effort` (low to max)** and Seatline refused it. The CLI treats a level it does not know as a warning and uses its default, so passing `none` through would silently replace the choice.
- **The data that tells these apart was thrown away.** Codex's `cached_input_tokens` and `reasoning_output_tokens` were dropped, Claude's cache reads and writes were merged into one total, and nothing recorded the time from the provider's final result to the terminal update.

**I-05 evidence.** What the wait is, measured with the adapter's command line, environment and process group (result line to exit, milliseconds): left alone 450 to 649 over five runs (median 552); SIGTERM at the result 396 to 528 (median 437), exit 0, the same wrap-up; SIGKILL 10 to 32, which in all five runs left `~/.claude/sessions/<pid>.json`, its `.key` and `/tmp/cc-socks/<pid>.sock` behind in the user's own directories; `DISABLE_TELEMETRY=1` or `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC=1` 19 to 24 over three runs each. A traced run shows the CLI opening a new TLS connection through the proxy after its result, sending one event-logging POST, removing its session file and exiting. So a signal does not shorten the wait and a kill is not clean: the turn stops waiting and the process finishes. The mechanism is `process::Reaper` (a helper thread per process, bounded; it waits `finish`, asks the process to stop and gives it `stop_grace`, then kills it; it gives the process back when full), `LineStream::release` (which refuses a process that has exited or lines still to deliver), and the Claude adapter releasing the process of a turn that succeeded and keeps no session when it reads the `result`. [`scripts/measure-claude-exit.py`](../scripts/measure-claude-exit.py) repeats the measurement on another CLI. The fake Claude gained `exits-after-<ms>` and `fails-after-<ms>`, which take that long to leave and record their exit only if allowed to get there. Six integration tests: the end at the result, with the whole answer, its usage (18, 5, 2 and 3 tokens as the fake reported them) and exactly one terminal update; the process then leaving on its own, which a signal or a kill would have prevented, and being reaped; a turn that keeps a session, and a failed one, still waiting for the process; a process that never leaves being stopped after the grace without holding the turn; the bound (the first turn takes the one place and the second waits for its own, and with no places every turn waits); and a cancel after the end reporting `Stopped` and leaving the process alone. Nine unit tests cover the reaper (including its being one for the whole process) and `release`. The cross-provider contract now gives Claude a moment to be reaped, as it gives the others none.

Live ([summary](performance-baselines/2026-10-09-claude-live-i05-summary.md)), in alternating runs of the previous commit and this change over 48 requests each: `submit→done` fell from 2330 to 1948 ms (**−382 ms**, 16 %) against differences of at most 41 ms between runs of one binary; `tail` from 439 to 0.1 ms; `completion` from 467 to 27 ms; `init` did not change (669 and 667 ms), so the next launch is not slowed by the last process still leaving; first text may be about 50 ms later, which is as large as the noise. In a run of all six scenarios every turn that keeps no session had a `tail` of 0.1 ms and the one that keeps a session was unchanged (476 ms). A sampler saw at most two Claude processes alive at once in 3,211 samples and no zombie, and no session files were left behind. The gain is for a one-word answer in one sandbox, the load was one request at a time, and Antigravity's and Grok's wait is still unmeasured.

**Not verified.** No live Codex, Gemini or Grok, so no baseline for them and no number for Antigravity's or Grok's wait after the answer, which I-05 therefore leaves alone. The Claude baseline is one sandbox with an account of unknown plan, ten samples per scenario (so no p95), a one-word answer and a home that loads almost nothing of its own: it supports where the time goes in that case, and nothing about another machine, a long answer, tools, or another model or effort. **Migration.** A full `Usage { .. }` literal adds `..Usage::default()`. `Exchange` and `Provider` gain defaulted methods (`result_at`, `refuses_reasoning_effort`), so custom adapters compile unchanged. Telemetry records gain two optional fields and the schema stays 1. `scheduling.json` gains an optional `claude_isolation`: a file without it behaves as before, and a broker from before this change refuses a file that sets it (unknown fields are refused), so the setting needs this version. `seatline-bench` gains `--policy` and the `prepared-send` scenario, and its reports gain `parameters.policy` (absent when none was given); older reports still load. A Claude turn that succeeded and keeps no session now ends when Claude prints its result, up to about half a second before its process has exited: an application sees the terminal update sooner and nothing else changes on the wire, and `tail_us` falls to next to nothing for those turns. Provider processes can briefly outnumber running generations, by at most the bound (8); `Claude::with_background_exits(0)` restores waiting for every turn. An application that offers an effort setting must offer `none` for Codex only: the capability is one flag for the adapter, not a list of levels.
