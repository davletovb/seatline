# Seatline performance implementation tracker

## Goal and scope

Reduce first-visible-text latency and recurring local overhead while keeping one shared companion safe for Tabbeam, Conclave, and Lineleaf. A warm broker, a resumed conversation, and a reused provider process are different states; report them separately.

Seatline owns provider execution, transport, readiness, scheduling, and cleanup mechanics. Applications retain prompts, conversation policy, orchestration, editor behavior, and product-specific preparation triggers. Keep the runtime Rust-based; do not add a JavaScript runtime or move Conclave features into Seatline.

Source review baseline: [`dc1086582c8b98498aa48dae91c8d174bc3cfc3c`](https://github.com/davletovb/seatline/tree/dc1086582c8b98498aa48dae91c8d174bc3cfc3c), rechecked against main on 2026-10-03. These are source-backed findings, not measured live-provider speedups.

## Workflow

- **READY**: dependencies satisfied; implementation may start.
- **IN PROGRESS**: actively being implemented.
- **BLOCKED**: finish the listed dependencies or protocol investigation first.
- **DEFERRED**: intentionally skipped pending an explicit project decision.
- **IMPLEMENTED — VERIFY**: code and local checks complete; PR/platform/integration validation remains.
- **DONE**: merged and the stated acceptance evidence is recorded.
- **EXTERNAL**: tracked here, but implementation belongs in an application repository.

Update this file in every implementation PR. Record commit/PR, relevant checks, measured evidence, and limitations. Verify each finding against the current code before changing it. Complete coherent slices; do not mark plans, prototypes, skipped live tests, or app work as finished library behavior.

## Implementation order

1. A: fix lifecycle bounds and remove the fixed startup delay.
2. B: establish reproducible phase measurements before claiming speedups.
3. C and D: define readiness freshness and reuse transport safely.
4. E: **deferred by user decision on 2026-10-04** pending the decision about Codex app-server; do not start the persistent-provider slice yet.
5. F: move blocking work off the hub, improve fairness, and reduce idle overhead.
6. G: validate and adopt the changes in all three applications.

D-01 and parts of B can proceed independently of C. Persistent-provider production rollout depends on B, C, and isolation/recovery evidence, rather than prototype existence alone.

## Verification and release gates

- Required for each Rust slice: formatting, workspace Clippy, workspace tests with the lockfile, affected regression tests, and the client-only companion build.
- Existing CI remains responsible for OS matrix, minimum Rust 1.85, release tests, runtime independence, and fuzz smoke. Real-provider tests remain opt-in.
- Lifecycle gates: one terminal event per accepted request, bounded cancellation/finish, eventual child reaping, no leaked occupied slots, no cross-app context or grant leakage.
- Performance gates: publish reproducible before/after evidence; preparation time and total cold work remain visible. A genuinely cold machine still has startup work, and network/model latency is outside Seatline's direct control.
- No automatic application pin updates or default persistent-mode rollout until the corresponding integration evidence exists.

## I — Answer latency: relay delivery, Claude effort, and where the time goes — 2026-10-09

Owner: Seatline/application maintainers. Status: **I-01 to I-03 IMPLEMENTED — VERIFY**; I-04 to I-10 are planned, each with the gate it waits on. Reviewed merged main at `af24567` ([PR #14](https://github.com/davletovb/seatline/pull/14)); the work is on branch `claude/perf-model-latency-slice-i` and is not yet a pull request. Slice E stays **DEFERRED** pending the Codex app-server decision.

The question was what is left to speed up between a request and the model's answer. Seatline's own share is small and mostly spent: a warm request reaches first text in about 1.5 ms with a fake provider ([F](performance-baselines/2026-10-04-f-hub-summary.md)), and the owner's manual timing recorded in H-03 put 19,009 ms of a 19,147 ms Lineleaf check in the answer phase, 138 ms (0.7 %) anywhere else. What remains is in how each provider CLI is launched and ended, in waits around the answer, in what the model is asked to do, and in not knowing where the answer time goes. These findings are source-backed. **No live-provider measurement was made, so no item here claims a speedup of a real answer.**

What the review found:

- **Claude loads the user's whole setup on every turn.** `claude -p` runs the user's hooks, plugins, skills and `CLAUDE.md` unless told not to. In a scratch home holding two synthetic 1-second hooks, Seatline's exact arguments took 5.7 s and the same arguments with `--safe-mode` 2.8 s (one run each, Claude CLI 2.1.295; that CLI had credentials of its own, so both runs sent a one-word prompt to a model). It is an observation, not a baseline: the cost on a real machine depends on its hooks and is unmeasured.
- **Three adapters wait up to 5 s for the process after the answer.** Claude, Antigravity and Grok hold `Completed` until the CLI exits (`turn_ended` in the Claude adapter, and the `FINISH_GRACE` of the other two); only a successful ephemeral Codex turn was changed (H-02). How long the wait is in practice is unmeasured, because telemetry marked the terminal update only after the process was gone, so the wait sat inside `completion`.
- **Readiness evidence lapses after 30 s** (`seatline_core::readiness::MAX_AGE`), so the first check after a quiet half minute runs a sign-in probe before generating. `claude auth status` took 280 to 570 ms here; `codex login status` was not timed.
- **At most two generations run per app and per provider**, a ceiling `scheduling.json` cannot raise (`Policy::validate`), so an application that splits one long job into parallel requests queues the third.
- **Codex reports each message whole**, so the first text of a one-message answer arrives with its end. Incremental text needs the app-server protocol (E-01).
- **The relay WebSocket left Nagle's algorithm on**: `connect_async` does not set `TCP_NODELAY`, and every event is its own small frame.
- **Claude's CLI has `--effort` (low to max)** and Seatline refused it. The CLI treats a level it does not know as a warning and uses its default, so passing `none` through would silently replace the choice.
- **The data that tells these apart was thrown away.** Codex's `cached_input_tokens` and `reasoning_output_tokens` were dropped, Claude's cache reads and writes were merged into one total, and nothing recorded the time from the provider's final result to the terminal update.

**I-01 evidence.** Each adapter's field mapping is pinned with a distinct number per field (the Codex fixtures are all zeros and cannot tell a swap apart): Codex's five counts, and an older Codex that reports totals only; Claude's cache reads and writes. All four adapters report their result time, for a success, for a failed result, and (Claude) a process that ends with none. The scheduler, the `Ready` wrappers and the hub's session gate pass the report on, and one that panics drops only itself. The real broker's records, joined by the bench harness against the fake Codex, carry the usage and a tail for every send and neither for a status check. Reports saved before the change still load (a test pins it, and the two checked-in `run` reports were rendered and compared by hand). The wire is pinned: the detail fields are not serialized, and a sender that includes them is read as before. The usage keys in a record omit the word "token", which the bench's credential check looks for.
